# Mebaco 検証アーキテクチャ方針

## 1. この資料の位置付け

本書は、Mebaco における静的検証とランタイム検証の責務、実行タイミング、将来の実装方針を定める引継ぎ資料である。

本書に記載する内容は目標設計であり、すべてが現時点で実装済みとは限らない。実装に着手する際は、対象範囲を改めて計画し、既存コードとテストの状態を確認すること。

Function、Action、Conditional など個別要素の機能仕様そのものは本書の対象外とする。ただし、それらに対してどのような整合検証を行うかは本書で扱う。

## 2. 基本思想

Mebaco の検証は、次の責務分離を基本とする。

1. ノード編集時は、そのノード要素に閉じた検証を行う。
2. 要素間依存を含む検証は、App 単位または Project 単位で明示的に行う。
3. App 起動前には、起動対象 App の整合性を検証する。
4. ファイル保存時には検証を行わず、現在の編集状態をそのまま保存できるようにする。
5. ランタイムでは重いツリー検証を繰り返さず、実行性能を優先する。
6. ランタイムで予期しないエラーが発生した場合は、安全に強制停止し、原因調査に必要な情報を専用エラー画面へ表示する。

不完全なツリーや起動できないツリーであっても、作業途中の状態として保存できることを保証する。保存可能であることと、App として実行可能であることは別の概念とする。

## 3. 検証レイヤー

### 3.1 要素単体検証

要素の作成・編集ダイアログ内で、その要素だけで判断できる内容を検証する。

対象例：

- 必須入力
- ID の文字種と長さ
- 数値範囲
- 同一フォーム内の重複
- 式の構文
- 編集時点のコンテキストを使った式の型推論
- 選択した型と入力値の整合

要素単体検証は入力中の即時フィードバックを目的とする。別ノードの将来状態まで保証するものではない。

例えば、Action 編集時に参照先が存在していても、その後に参照先ノードが削除されれば、Action は不整合になり得る。この種の問題は App または Project の整合検証で検出する。

### 3.2 App 整合検証

起動対象 App と、その App から到達可能な依存要素を対象に検証する。

実行タイミング：

- App 起動時に自動実行
- ユーザー操作による手動実行

エラーがある場合、App のランタイム生成や Retention 初期化を開始してはならない。警告だけの場合に起動を許可するかは、ルールごとの severity 方針で決める。

App 整合検証は、単純に App ノードの子孫だけを検査するものではない。次も対象に含める。

- App 配下の全要素
- App から参照される Common 要素
- 参照先から推移的に参照される Function、Object、Union など
- App の式や設定から参照される共有定義

未使用の別 App と、その App からしか到達できない要素は対象外とする。

依存グラフには再帰 Function などによる循環があり得るため、検証済み集合を使って無限走査を防止する。

### 3.3 Project 整合検証

Project 全体と、すべての App、Common、共有定義を対象に検証する。

実行タイミング：

- ユーザー操作による手動実行のみ

対象例：

- 全 App の整合性
- Common と共有定義の整合性
- Project 全体で必要な一意性
- 参照切れ
- 到達不能または未使用の定義に関する警告
- App 間または共有領域間の禁止された依存

Project 整合検証も保存処理とは連動させない。

### 3.4 ランタイム検証

ランタイムでは、ツリー全体の走査、全式の型解析、全依存の再解決など、重い検証を実行ごとに行わない。

App 起動前の静的検証を通過したツリーのスナップショットを、ランタイムの前提とする。

ランタイムに残す検査は、次のような低コストの Assert と境界チェックに限定する。

- 必須の内部オブジェクトが存在する
- 実行対象の要素kindが想定どおりである
- コンパイル済み処理の戻り値が最低限の契約を満たす
- 到達不能と想定した内部状態へ到達していない
- 外部APIやユーザー式が例外を送出していない

ランタイムエラーは握りつぶさず、中央のエラー境界へ伝播させる。エラー発生後は対象 App の実行を停止し、部分的に変更されたランタイム状態を継続利用しない。

## 4. 実行タイミング一覧

| タイミング | 要素単体 | App整合 | Project整合 | ランタイムAssert |
|---|---:|---:|---:|---:|
| ノード編集時 | 実行する | 実行しない | 実行しない | 実行しない |
| App手動チェック | 必要に応じて再利用 | 実行する | 実行しない | 実行しない |
| Project手動チェック | 必要に応じて再利用 | 全App分を実行 | 実行する | 実行しない |
| App起動時 | 必要に応じて再利用 | 実行する | 実行しない | 起動後に実行 |
| ファイル保存時 | 実行しない | 実行しない | 実行しない | 実行しない |
| ファイル読込時 | ファイル形式のみ確認 | 原則実行しない | 原則実行しない | 実行しない |

ファイル読込時は、JSONやアーカイブとして読み取れること、対応するスキーマ世代であることなど、デシリアライズに必要な最低限の確認だけを行う。App としての整合性は起動時または手動チェック時に判断する。

## 5. App 起動制御

App 起動は次の順序で行う。

```text
起動対象 App を決定
  ↓
編集ツリーのスナップショットを確定
  ↓
AppValidator で整合検証
  ↓
エラーあり ─→ ランタイムを作らず、検証結果を表示
  ↓ エラーなし
ランタイムコンテキストを生成
  ↓
Retention を初期化
  ↓
App を起動
```

検証より先に Retention や Action を実行してはならない。検証エラーが見つかった時点で、外部作用や State 変更が発生していないことを保証する。

手動 App チェックと App 起動前チェックは、同じ `AppValidator` と同じルールセットを使用する。別実装にして判定差を作らない。

## 6. 検証対象の式

最終的には、ツリーに保存されるすべての実行式を App／Project 整合検証の対象とする。

対象例：

- Action のスクリプト
- Variable の初期式
- State の初期式
- Function Return の式
- Conditional の条件式
- Component Binding の式
- イベントAction
- Style の条件式
- Ref の式
- 要素固有のFormula

式の検証では、最終的なツリーからスコープと型宣言を再構築する。これにより、編集後に削除・移動・改名された次の参照を検出する。

- `$var.<id>`
- `$state.<id>`
- `$args.<id>`
- `$function.<id>(...)`
- Object／Union などの型参照
- Component、Style、Ref などの要素参照

式の構文解析だけでなく、可能な範囲で引数数、Nullable、配列、Object、Union、戻り値型も検証する。

## 7. 動的アクセスの制約

JavaScript式を許可する以上、次のような動的アクセスは完全な静的検証ができない。

```ts
$state[key]
$function[name]()
```

静的検証を保証したいシステム名前空間では、原則として静的なプロパティアクセスを使用する。

```ts
$state.currentUser
$function.calculate()
```

動的アクセスを禁止するか、静的保証の対象外としてランタイム責任にするかは、名前空間ごとに明文化する。少なくとも `$function` は、静的な `$function.<id>(...)` 形式を基本とする。

外部API、ネットワーク、ユーザーデータに依存する失敗は静的には保証できないため、ランタイムエラーとして扱う。

## 8. Function の制御フロー検証

将来 Conditional を Procedure に導入する場合、非Void Functionでは、すべての到達可能な正常終了経路に Return が必要となる。

Void Functionでは Return は必須ではないが、条件分岐内の早期Returnを許可できる。Void Return は値を返す式を持たない。

### 8.1 基本ルール

- 非Void Functionは、Procedure終端へそのまま到達する経路を持ってはならない。
- 非Void Returnは、定義された戻り値型と互換な式を持つ。
- Void Returnは式を持たない。
- Returnはその制御経路を終了する。
- Returnの後ろにある同一経路上の要素は到達不能である。
- 到達不能要素をエラーにするか警告にするかは、severity方針で決める。

### 8.2 If／Else の解析

If／Else までの制御フローは、各ノードが後続へ到達可能かを返すことで解析できる。

```text
If condition
├─ Then → Return
└─ Else → Return
```

この場合、Ifの後続へ到達する経路はない。

```text
If condition
└─ Then → Return
```

Elseがないため、conditionがfalseの経路は後続へ到達する。後続にもReturnがなければ、非Void Functionではエラーとなる。

### 8.3 将来のLoop

Loopを追加する場合、次を考慮する必要がある。

- 0回実行される可能性
- `break` と `continue`
- Loop内部のReturn
- 無限ループを終端とみなすか

初期の制御フロー検証はIf／Elseを対象とし、Loop追加時に制御フローモデルを拡張する。Action内部で発生し得る例外は、原則として正常なReturn経路とはみなさない。

## 9. 検証基盤の責務

検証基盤は、ツリーを書き換えない純粋な処理として実装する。

想定API：

```ts
type ValidationIssue = {
  code: string
  severity: 'error' | 'warning'
  message: string
  nodeId?: number
  relatedNodeIds?: number[]
  path?: string[]
}

type ValidationResult = {
  issues: ValidationIssue[]
}

AppValidator.validate(projectRoot, appNodeId): ValidationResult
ProjectValidator.validate(projectRoot): ValidationResult
```

`code`は表示文言とは別の安定した識別子とする。テストや将来の自動修復、問題一覧のフィルタリングで使用する。

検証結果には、可能な限り次を含める。

- 問題のあるNode ID
- 関連するNode ID
- App ID
- 要素kind
- Function IDなどの論理名
- 依存経路
- 式内の位置

手動チェックUIでは、問題一覧から対象ノードへ移動できるようにする。

## 10. 要素ごとの検証情報

すべての要素を対象に拡張するため、中央バリデーターへ要素kindごとの巨大な分岐を集約しない。

各要素定義が、必要に応じて次の情報を検証基盤へ提供する方式を検討する。

- 要素が保持する式
- 式のモード（Formula／Action／Conditionなど）
- 期待する型
- 参照しているNodeや型
- 許可する子要素
- 要素固有の整合ルール

中央のApp／Project Validatorは、検証対象の収集、依存解決、実行順序、結果統合を担当する。

要素単体のフォーム検証と、ツリー全体の検証ルールは再利用できる部分を共有してよいが、UI状態へ依存させない。

## 11. コード配置

ツリー整合検証は、UI入力検証やファイル保存処理から分離する。

想定配置：

```text
src/system/validation/
├─ validation-issue.ts
├─ validation-result.ts
├─ app-validator.ts
├─ project-validator.ts
├─ dependency/
├─ expression/
├─ control-flow/
└─ rules/
```

`src/system/ui/validation/`に存在する入力表示用の仕組みとは責務が異なる。ツリー整合検証からUIコンポーネントやダイアログストアを直接参照しない。

ファイル保存処理から `AppValidator` や `ProjectValidator` を呼び出してはならない。

## 12. パフォーマンス方針

App 起動前チェックでは、対象Appと到達可能な依存だけを検証する。

式ごとにTypeScript Programを新規生成する方式は避け、可能な限り次を行う。

- 対象式をまとめた解析単位を作る
- TypeScriptの解析環境を共有する
- ツリーリビジョンまたは内容ハッシュ単位で結果をキャッシュする
- 変更された要素と依存先だけを再検証する
- 手動チェックと起動前チェックで結果を共有する

同じツリースナップショットに対して検証済みであれば、App起動時にキャッシュ結果を再利用できる。ただし、キャッシュキーにApp、ツリーリビジョン、検証ルール世代を含める。

ランタイムではFunction呼び出しごとにツリー走査やTypeScript解析を行わない。

## 13. ランタイムエラー処理

静的検証で完全に防げないエラーは、ランタイムの中央エラー境界で捕捉する。

対象例：

- ユーザー式が送出した例外
- 外部APIエラー
- 非同期処理のreject
- 実データと宣言型の不一致
- 内部Assert違反
- 実装上想定していない要素状態

専用エラー画面には、可能な限り次を表示する。

- App ID
- Node ID
- 要素kind
- Function ID
- 実行ステージ
- 元のエラーメッセージ
- Function呼び出し履歴
- 式の位置
- 再起動または開発画面へ戻る操作

同期例外、Promiseのreject、イベントActionからの例外を同じ形式へ正規化する。

エラー発生後は対象Appを強制停止する。再実行時はランタイムコンテキストと一時Stateを作り直し、部分実行後の状態を継続利用しない。

## 14. 実装を段階化する場合の推奨順序

実装開始時には各段階を改めて計画し、段階ごとに動作確認する。

1. `system/validation`の共通型と純粋なValidator APIを定義する。
2. 要素から式と依存情報を収集する仕組みを定義する。
3. FunctionとIf／Elseの制御フロー検証を実装する。
4. 起動対象Appの依存閉包を収集するApp Validatorを実装する。
5. App起動前のブロック制御と検証結果画面を実装する。
6. App手動チェックとノード移動UIを実装する。
7. Project ValidatorとProject手動チェックを実装する。
8. 式解析の共有、キャッシュ、差分検証を実装する。
9. ランタイムの中央エラー境界と専用エラー画面を実装する。

最初のルールがFunctionだけであっても、Function専用の保存バリデーターとして作らず、App Validatorのルールの1つとして追加する。

## 15. 決定事項

- 保存は常に可能とし、整合検証を実行しない。
- App起動時には、対象Appの整合検証を実行する。
- App整合検証は手動でも実行できるようにする。
- Project整合検証は手動実行とする。
- App検証は到達可能なCommon依存を含める。
- 検証はツリーを自動修復しない。
- 重い要素間依存検証はランタイムから外す。
- ランタイムには軽量Assertと中央エラー処理を残す。
- 非Void Functionは全正常終了経路でReturnを必要とする。
- Void FunctionはReturnを必須とせず、早期Returnを許可する。
- 動的アクセスは静的検証の限界を明示する。
- ツリー整合検証は `system/validation` 配下で管理する。

## 16. 未決事項

実装前に、少なくとも次を決定する。

- Conditional要素の正確なツリー構造
- Elseを固定要素にするか任意要素にするか
- 到達不能要素をerrorとwarningのどちらにするか
- 動的なシステム名前空間アクセスを禁止する範囲
- App検証の警告が起動を妨げるか
- 検証結果キャッシュに使用するツリーリビジョン方式
- Loop、break、continue導入時の制御フロー規則
- Runtime Error画面で表示・保存する診断情報
- 既存の不整合データに対する移行・正規化方針
